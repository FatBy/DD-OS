# 文风指纹（Writer Fingerprint）设计文档

> 适用模块：DunCrew 自习室（StudyRoom）
> 代码位置：`src/services/studyRoom/` + `src/components/houses/studyRoom/sidebar/`
> 文档版本：对应代码 v3（formatFingerprintV2 + L0 行为规则）

---

## 一、为什么要做文风指纹

### 1.1 我们在解决什么问题

自习室是 DunCrew 里专门做"长文写作"的工作台。在没有文风指纹之前，LLM 写出来的东西有几个顽疾：

- **千人一面的"AI 体"**：不管写什么，句长、转折、用词都是同一副 ChatGPT 腔。
- **全文风格不一致**：第一段像散文，第二段像报告，第三段又像公众号推文。
- **用户的声音被抹平**：用户自己有一摞之前写过的、满意的稿子，但没办法告诉 AI "就按这种风格写"。

提示词里塞几句 "请用 XX 风格" 治标不治本——LLM 每轮都要自己猜 XX 是什么意思，跨段就会漂移。

### 1.2 文风指纹的产品定位

> **文风指纹是从用户已有的稿子里提炼出的、可复用、可迭代的"作者人格模板"。**

一句话概括使用链路：

```
用户丢进 3~5 篇自己写的稿子
       ↓
系统提炼出一份"文风指纹"（JSON + 行为规则）
       ↓
用户在自习室写新文章时把它"激活"
       ↓
LLM 以"我就是这个作者"的人格去写每一段
```

关键设计选择：**不是让 LLM 去"模仿风格"，而是让它"成为这个作者"。** 这一差别直接决定了 prompt 的拼装方式（后文 §4 细讲）。

### 1.3 为什么要做三层（其实是四层）分层

指纹内部结构上分 L0 / L1 / L2 / L3 四层，每层各司其职：

| 层 | 内容 | 给谁看 | 作用 |
|---|---|---|---|
| **L0 行为规则** | `when / do / not / examples` 的可执行规则 | 主要给 LLM | 最接地气的"这种场景就这样写"的肌肉记忆 |
| **L1 量化指标** | 句长、短长句比、成语密度等 | 主要给 UI + LLM 锚点 | 提供客观数字，避免主观描述飘忽 |
| **L2 六层画像** | 22 维度的自然语言描述（句式/论证/说服/态度/意象/结构） | 给人看 + LLM 参考 | 可视化、可编辑的"风格档案" |
| **L3 范文样本** | 原文里的代表性段落 | 给 LLM 做 few-shot | 最硬核的"这就是我的声音" |

分层的核心意义：**不同维度用不同手段表达最自然**。句长适合数字、论证模式适合枚举、情绪温度适合词汇、具体写法适合范文——硬塞到一个维度里会丢信息。

## 二、数据模型

所有类型定义在 `src/types.ts`（从 L3114 起）和 `src/services/studyRoom/fingerprintSchema.ts`。

### 2.1 顶层结构：`WriterFingerprint`

```ts
// src/types.ts
export interface WriterFingerprintMeta {
  id: string
  name: string              // 显示名，如"鲁迅杂文体"
  description?: string      // 用户自述
  sourceCount?: number      // 源文档数
  sourceWordCount?: number  // 源文档总字数
  createdAt: number
  updatedAt: number
}

export interface WriterFingerprint extends WriterFingerprintMeta {
  profile: WriterFingerprintProfile           // L2 画像
  metrics: WriterFingerprintMetrics           // L1 指标
  samples: WriterFingerprintSample[]          // L3 范文
  behaviorRules?: FingerprintBehaviorRule[]   // L0 行为规则（可选）
  sourcePaths?: string[]                      // 源文件路径
  distillLogs?: WriterFingerprintDistillLog[] // 提炼日志（便于回溯）
}
```

列表页只读 `WriterFingerprintMeta`（元信息），详情页才按需加载完整对象——避免一次性把上千字的范文全读出来。

### 2.2 L0 行为规则：`FingerprintBehaviorRule`

```ts
export interface FingerprintBehaviorRule {
  when?: string       // 内部触发条件（判断式，不是位置）
  do?: string         // 作者具体怎么做
  not?: string        // 作者明确不做什么
  examples?: string[] // 多源印证（≥2 条，来自原文不同位置）
  // 向后兼容字段：example / rule / trigger / antiExamples 等
}
```

**两个关键认知论升级**（代码注释里有详细哲学依据）：

1. **维特根斯坦"共识是涌现的"**：一条规则的意义 = 它在不同使用场景下的交集。所以 `examples` 是复数且要求 ≥ 2 条——只出现一次的写法是"偶然"，不是"规则"。
2. **"语言游戏的语境分层"**：`when` 可以横跨三个层级，都共用同一个容器：
   - 微观（句子/段内）："当需要自嘲时"
   - 中观（段落/论证）："当面对可能抵触的读者时"
   - 宏观（篇章/骨架）："当决定开篇切入角度时"

反面教材（`when` 字段的错误写法）：
- ❌ "开头第一段" / "段落过渡处" → 这是排版习惯，不是风格
- ✅ "当想给一个论断减轻权威感时" → 这才是作者的内部判断

### 2.3 L1 量化指标：`WriterFingerprintMetrics`

```ts
export interface WriterFingerprintMetrics {
  avgSentenceLen?: number       // 平均句长（字）
  avgParagraphLen?: number      // 平均段长（字）
  shortSentenceRate?: number    // 短句（<15 字）占比 0~1
  longSentenceRate?: number     // 长句（>40 字）占比 0~1
  formalityScore?: number       // 书面/口语倾向 -1~+1
  idiomDensity?: number         // 成语密度 个/千字
  rhetoricRate?: number         // 设问/反问率 个/千字
  // 扩展指标（全部可选）：
  // conjunctionDensity / modalDensity / questionDensity / rhetoricalQuestionRate /
  // assertionDensity / addressYou / addressYouFormal / addressWe / addressEveryone
  [extra: string]: number | undefined
}
```

全部字段都可选。后端 `/api/study/fingerprints/distill-prepare` 负责计算，计算不出的指标直接缺省不报错。扩展字段通过 `[extra: string]` 索引签名做前向兼容——后端新增指标不会打破旧客户端。

### 2.4 L2 六层画像：`WriterFingerprintProfile`

22 个可选字段分 6 层（权威定义在 `fingerprintSchema.ts` 的 `PROFILE_FIELD_SPECS`）：

| 层（layer） | 中文标签 | 字段 |
|---|---|---|
| `micro` | 微观语言层 | sentenceStyle / rhetoric / vocabulary / paragraphing / citation / avoid |
| `discourse` | 话语/论证层 | argumentPattern / evidencePreference / counterArgHandling / argumentDepth / transitionStyle / informationDensity |
| `persuasion` | 说服力层 | appealBalance / emotionalTriggers / credibilityBuilding |
| `stance` | 态度层 | certaintyLevel / emotionalTemperature / readerDistance |
| `semantics` | 意象/主题层 | frequentImagery / metaphorDomain / referencePreference |
| `macro` | 宏观结构层 | hookPattern / pacingPattern / turnPoints / closingPattern |

**字段的 3 种形态**（由 `ProfileFormShape` 定义，驱动渲染和解析）：

```ts
export type ProfileFormShape = 'string' | 'enum' | 'enumPair' | 'appeal'
```

- **string**：纯描述型。如 `sentenceStyle`（句式特点）、`avoid`（明确避免）。
- **enum**：单选枚举 + 描述。如 `hookPattern: { type: 'scene' | 'question' | ..., description }`。
- **enumPair**：主+次枚举 + 描述。如 `argumentPattern: { primary, secondary?, description }`——一个作者可能"主因果推论、次对比论证"。
- **appeal**：Logos/Pathos/Ethos 三段配比（亚里士多德修辞三诉诸），总和归一到 1：
  ```ts
  appealBalance?: { logos: 0.6, pathos: 0.1, ethos: 0.3, description: '...' }
  ```

**意象/主题层的特殊处理**：`frequentImagery` / `metaphorDomain` / `referencePreference` 三个字段有 `requiresMultiSample: true` 标记——源文档数 < 3 时，LLM prompt 里会强制要求跳过这些字段，避免单篇样本凭感觉编"高频意象"。阈值常量 `MULTI_SAMPLE_THRESHOLD = 3` 定义在 `styleFingerprint.ts`。

### 2.5 L3 范文样本：`WriterFingerprintSample`

```ts
export interface WriterFingerprintSample {
  text: string      // 样本正文
  source?: string   // 来源标题（如 "《散步》"）
  reason?: string   // 入选理由（如 "最能体现画面感"）
}
```

范文由后端在 `distill-prepare` 阶段抽取（启发式抽代表性段落），L0 提取时 LLM 还可能补充更好的候选，最后由 `dedupSamples`（按文本前 50 字去重）合并，截断保留 6 段。

## 三、提炼流水线

入口：`distillFingerprint(req, onProgress, llmProfileDistiller?, llmL0Extractor?)`（`styleFingerprint.ts` L378）。

整条管线分阶段 emit 进度，UI 侧（`DistillDialog.tsx`）订阅进度流实时渲染日志时间线和流式 token。

### 3.1 全景流程图

```
用户在 FingerprintPanel 点"从文档提炼新风格"
  ↓
DistillDialog 收集源文档 + 命名 + 可选 baseRefine
  ↓
distillFingerprint(req, onProgress)
  │
  ├── 阶段 1：reading（10%）
  │   POST /api/study/fingerprints/distill-prepare
  │   后端：读文件 → 计算 L1 指标 → 抽候选范文 → 返回 combinedText
  │
  ├── 阶段 2a：llm_profile（50~70%）
  │   前端调 llmProfileDistiller（用户配置的 LLM）
  │   输入：L1 指标 JSON + combinedText + (打磨模式时 baseProfile 锚点)
  │   输出：L2 六层画像（parseProfileFromLlm 严格校验）
  │   特性：流式 token 实时 emit 给 UI，占位日志原地更新
  │
  ├── 阶段 2b：llm_l0（72~82%）（可选，未配置则跳过）
  │   前端调 llmL0Extractor
  │   输入：profile + 指标 + combinedText + (打磨模式时 baseRules 锚点)
  │   输出：L0 行为规则 + 可能产出的更好范文
  │   失败保护：L0 失败不阻断，降级为没有 behaviorRules
  │
  ├── 阶段 3：preview（85%）
  │   组装 draft（不落盘！）
  │   打磨模式：按 0.4:0.6 权重合并指标 + 去重合并样本 + 规则指纹去重合并
  │   emit 'preview' 把 draft 交给 UI
  │
  └── 阶段 4：saving → done（92~100%）
      用户在预览页点"保存"，才调 commitDistilledFingerprint
      saveFingerprint 先写 localStorage，再尽力同步后端
```

### 3.2 阶段 1：后端准备（reading）

```ts
// styleFingerprint.ts L431
const prepRes = await fetch(`${API_BASE}/api/study/fingerprints/distill-prepare`, {
  method: 'POST',
  body: JSON.stringify({ sources: req.sources }),
})
```

后端（`duncrew-server.py`，端口 3001）返回：

```ts
{
  combinedText: string            // 拼接后的全文（供 LLM 输入）
  metrics: WriterFingerprintMetrics // L1 指标
  samples: WriterFingerprintSample[]// 候选范文
  sourceCount: number
  sourceWordCount: number
  sourcePaths?: string[]
}
```

**关键架构决定**：指标计算放后端做，LLM 推理放前端做。原因：
- LLM 调用要复用用户在设置里配置的 key/model，不能在后端硬编码。
- 指标算法（分句、分词、成语匹配）用 Python 生态更顺手，也方便后续沉淀为库。

### 3.3 阶段 2a：L2 画像生成（llm_profile）

由调用方（`DistillDialog`）注入 `llmProfileDistiller`，避免服务层直接依赖 LLM 客户端造成循环。

```ts
export type LlmProfileDistiller = (args: {
  combinedText: string
  metrics: WriterFingerprintMetrics
  name: string
  sourceCount: number
  isMultiSample: boolean           // < 3 篇时禁用意象层
  basePrompt: null | {             // 打磨模式锚点
    baseProfile: WriterFingerprintProfile
    baseName: string
  }
  onStream?: (ev: LlmStreamEvent) => void
}) => Promise<LlmProfileResult>
```

**流式占位日志机制**（`flushStreamingLog`）：
- LLM 请求一发出，就在 logs 里 push 一条 `label="LLM 推理中..."` 的占位。
- 每收到一块 token 原地更新这条日志的 `detail` 和 `label`，节流 180ms / 累积 60 字才 emit 一次。
- 收尾把占位定格成 `level: 'success', label: '推理完成 (1234ms · reasoning 500 字 / content 2000 字)'`。
- 失败时占位变红，保留已产出的片段 + 错误堆栈。

这样用户不会干等 10~30 秒以为卡死，也方便事后调试"LLM 到底看到了什么、想了什么"。

**Schema 约束**：prompt 里用 `buildProfileSchemaPrompt(isMultiSample)` 生成完整的 JSON Schema 说明，LLM 返回后走 `parseProfileFromLlm` 严格校验：
- 字段类型不对 / 枚举值非法 / 描述为空 → 丢弃该字段（不抛错）
- 返回 `{ profile, warnings }`，warnings 写入日志供用户查看"哪些字段被丢弃了"

`appealBalance` 还有专门的归一化：总和偏离 1 超过 0.05 会自动按比例归一；全 0 视为 LLM 没理解，直接丢弃。

### 3.4 阶段 2b：L0 行为规则提取（llm_l0）

只有同时满足 `llmL0Extractor 存在 && profile 非空` 时才触发。L0 是可选增强层，没有也不影响主功能。

```ts
export type LlmL0Extractor = (args: {
  profile: WriterFingerprintProfile  // 以 L2 画像为锚
  metricsJson: string
  combinedText: string
  name: string
  baseRules?: FingerprintBehaviorRule[]  // 打磨模式迭代锚点
  onStream?: (ev: LlmStreamEvent) => void
}) => Promise<LlmL0Result>
```

**关键设计：以 L2 为锚而不是从零提取**
L0 提取器拿到的是已经归纳好的 L2 画像，它的工作是"把画像里抽象的描述落到原文的具体位置去做多源印证"——这种带锚点的提取比从零猜规则稳定得多。

### 3.5 阶段 3：打磨模式（isRefine）的合并策略

打磨模式 = 对已有指纹 `refineBase` 用新稿件继续迭代。核心设计哲学：**绝不让好的旧数据凭空消失**。

**指标合并**（`mergeMetrics`，L876）：按 `旧 0.4 : 新 0.6` 加权
```ts
merged[k] = a * 0.4 + b * 0.6  // a = 旧值, b = 新值
```
新的权重更高（作者风格在进化），但旧值仍保留 40% 惯性。

**样本合并**（`dedupSamples`）：按文本前 50 字去重，优先保留 L0 提取器新产出的样本（通常更贴合规则），最多 6 段。

**行为规则合并**（`mergeBehaviorRules`，L925）：最精巧的部分。
- **指纹算法**：`normalize(when) + '|' + normalize(do)`
  - `normalize` = 小写 + 空白折叠 + 去标点
  - 选 when+do 是因为它们共同界定了"这是关于什么情境下做什么"——`not` 和 `examples` 会因打磨而变化，不参与同一性判断
- **合并规则**：
  1. 新规则先全部保留（按 LLM 返回顺序 = 区分度降序）
  2. 旧规则里指纹未被新规则覆盖的，追加到末尾
  3. 重复的旧规则丢弃（LLM 已经保留或升级过它）

**三级失败保护**（`mergedBehaviorRules` IIFE，L813）：
| 情境 | 行为 |
|---|---|
| 非打磨 | 直接用新规则（可为空） |
| 打磨 + L0 成功出新规则 | `mergeBehaviorRules(新, 旧)` 做确定性兜底 |
| 打磨 + L0 失败或无产出 | **保留旧规则不擦除**，并 push 一条 warn 日志 |

最后这一条是关键——如果 LLM 某次调用网络波动失败了，用户不应该因此丢掉之前辛苦打磨出来的规则。

### 3.6 阶段 4：预览 + 保存分离

```ts
emit('preview', 85, isRefine ? '预览打磨后的指纹' : '预览提炼出的指纹', { draft })
// distillFingerprint 在这里返回 draft, 不落盘
return draft
```

`distillFingerprint` 返回草稿后，主动权就交给 UI。用户在 `DistillDialog` 的预览页可以：
- **保存**：调 `commitDistilledFingerprint(draft)` → `saveFingerprint` → 落 localStorage + 尽力 PUT 后端
- **取消**：什么都不做，草稿丢弃，原有指纹完全不受影响
- **重试**：关闭对话框重开，重新跑一遍

"提炼 → 预览 → 保存"三段分离的设计让"无破坏性"成了代码层面的保证——任何失败都不会污染已有数据。

## 四、生成侧注入：指纹如何进到写作 prompt

代码在 `src/services/studyRoom/prompts.ts`。写作侧有两套注入函数：

| 函数 | 用途 | 注入内容 | 当前状态 |
|---|---|---|---|
| `formatFingerprint(fp)` | 旧版（v1/v2） | L2 画像 + L1 指标 + L3 范文的列表式结构 | 部分场景（提纲、篇幅复核等）仍在用 |
| `formatFingerprintV2(fp)` | v3 新版 | 第二人称独白的"人格召唤" + L0 规则 + 范文作为"过往作品" | 正文草稿/重写的主路径 |

### 4.1 Brief 关联：`resolveFingerprintForBrief`

```ts
// prompts.ts L395
export function resolveFingerprintForBrief(brief: WritingBrief): WriterFingerprint | null {
  if (brief.fingerprintId) {
    return getFingerprintSync(brief.fingerprintId)
  }
  return null
}
```

**关键设计决定**：指纹的生效是 **session 级别** 的，不是全局级别。

代码注释里明确写了权衡：
> 设计权衡：之前讨论时考虑过"active"全局激活模式，但容易造成"用户以为 session 没指纹结果其实默默应用了"，所以改为每个 session 显式指定。

`getActiveFingerprintId()` 仍然存在，但它仅作为"最近用过哪个"的 UI 暗示，**不会自动生效到 prompt**。每次新开 session 都要手动点"应用"。

### 4.2 v3 的核心理念：`formatFingerprintV2`

函数在 `prompts.ts` L1767。它做了一个反直觉的设计——**把 L1 指标和 L2 画像从写作 prompt 里移除了，只保留 L0 规则和 L3 范文**。

代码注释里给出了理由：

> 把 L0 行为规则从"外部 checklist"改造成"作者的第二人格独白"，让 LLM 进入 style-absorption 模式而非 compliance-checking 模式。
>
> 旧版 `1. **When**, Do 2. ✗ Not 例: xxx` 的列表结构，会触发 LLM 的"逐条核对合规"模式——它会把风格当成必须通过的检查项，而不是要内化的声音。新版用 `每当X, 你Y. 你不会Z. 你曾经这样写过...` 的独白式表达，让 LLM 在推理时以"我就是这个人"的视角运作，风格才会渗透进句子。

生成出来的 prompt 段落大致长这样：

```markdown
## 请你成为这位作者: 鲁迅杂文体

> 犀利、反讽、句子短促但信息密度高

接下来你要写的不是"符合某个风格指南的文章", 而是"这个人会写出的文章".
下面描述的是 ta 根深蒂固的写作习惯, 请把它们当作你自己的反射, 不是条款...

### 你的写作习惯

- 每当面对权威论断时, 你会用一个具体的场景反问让读者自己看见破绽. 你不会直接点破立场.
  （你曾经在不同地方这样写过:
    · "从来如此, 便对么?"
    · "不惮以最坏的恶意..."
  ）

- 每当论述快要滑向抽象时, 你会突然插入一个日常物事的特写. 你不会连续写超过三句抽象议论.
  （你曾经这样写过: "……那老大的、似乎总想爬到天上去的红鼻子"）

### 你过去的一些段落 (这是你的声音, 不是模板)

读完下面的片段, 不要去复制其中的句子或论点 —
要捕捉的是语气的温度、节奏的呼吸、转折的方式. 让它们变成你的肌肉记忆.

**片段 1** (出自《灯下漫笔》):
> ...

---

现在, 用这个人的声音去写. 不要在文章里解释你为什么这么写,
不要列"我遵循了规则 1/2/3", 不要在结尾自我点评. 直接写.
```

**三级降级策略**：

| 指纹状态 | 注入策略 |
|---|---|
| 有 `behaviorRules` + 有 `samples` | 人格独白 + 过往作品（完整版） |
| 仅有 `samples` | 纯 few-shot（当作品样本用） |
| 仅有 22 维 `profile` | `extractPseudoRulesFromProfile` 挑描述型字段转伪规则（第二人称叙事口吻） |
| 什么都没有 | 返回空串，不注入 |

### 4.3 用户风格档案 vs 指纹的优先级

自习室还有另一套"用户写作风格档案"（`WriterStyleContext`，来自长期记忆系统）。有指纹时档案会让位，但保留一条硬红线。代码在 `formatWriterStyleContext`（L220）：

| 情境 | preferences（历史偏好） | avoidPatterns（反感清单） |
|---|---|---|
| 无指纹 | 硬约束"必须遵守" | 硬约束 |
| 有指纹 | **降级为软参考**，与指纹冲突让位 | **仍是硬红线**——用户明确反感的东西永远不该写 |

理由：用户以前爱用的某种句式，切指纹后不应该把新指纹盖掉；但用户明确反感的（比如 "千万别用'让我们一起'开头"）无论用什么指纹都不该违反。

### 4.4 在写作管线中的注入点

`writingService.ts` 里凡是调用 LLM 写作的地方都走同一条注入链：

```ts
// writingService.ts L1401-1406（正文草稿）
const appliedFingerprint = resolveFingerprintForBrief(brief)
const fingerprintBlock = formatFingerprintV2(appliedFingerprint)
// ... 调 buildDraftPrompt({ brief, pool, memorySnippets, fingerprintBlock, ... })
```

旧版 `formatFingerprint` 仍被 `buildAgendaPrompt`（提纲生成）、篇幅复核等场景使用——这些场景需要画像的元信息来辅助结构决策，不纯是"写句子"，所以保留了画像注入。

两者注入时机都在 prompt 的 **开头**——优先级最高，放在证据池、记忆、技能之前。

## 五、使用指南（给用户）

### 5.1 第一次提炼一个文风

1. 打开自习室，在右侧边栏找到 **文风指纹** 面板（调色板图标 🎨）。
2. 点顶部的 **从文档提炼新风格** 按钮。
3. 在 `DistillDialog` 里：
   - 添加 3~10 篇你已有的、想要复现其风格的稿子（可以是 `.md` 文件或直接粘贴文本）。
   - 起个名字（如"鲁迅杂文体" / "我的公众号腔"）。
   - 可选填一句描述（只给人看，不注入 prompt）。
4. 点 **开始提炼**，观察左侧日志时间线：
   - "读取完成 X 篇 / Y 字" → 后端完成
   - "LLM 推理中..."（流式）→ 画像生成
   - "L0 提取完成 (N 条规则)" → 行为规则提取
   - "草稿已生成，等待用户确认保存" → 进入预览
5. 在预览页检查生成质量：
   - 六层画像的每个维度点开看有没有明显失真
   - L0 规则看每条的 when/do 是不是真的抓到了作者的特点
   - 范文样本是不是真的最能代表这种风格
6. 觉得 OK 就点 **保存**；觉得不对可以直接关闭重来（不会污染已有数据）。

> **建议最少 3 篇**。< 3 篇时意象/主题层会被强制跳过（见 §6.2），画像会不完整。

### 5.2 激活指纹到当前写作

提炼完成后，指纹出现在面板的指纹列表里，但**默认不生效**。

1. 进入你要写作的自习室 session。
2. 在指纹列表里点某一条的 **应用** 按钮（或直接点卡片）。
3. 看到顶部出现琥珀色提示 **"本会话正在应用: XXX"** 就说明激活成功。
4. 之后这个 session 里所有的"草稿生成 / 段落重写 / 提纲生成"都会自动带上这个指纹。
5. 再点一次同一条可以取消应用。

**切换 session 时注意**：指纹的激活状态是 session 级别的，新开 session 不会继承旧 session 的指纹——这是刻意的设计（见 §4.1）。

### 5.3 打磨（refine）一个已有指纹

打磨 = 用新的稿件继续迭代同一个指纹，适用于：
- 第一次提炼完用了几次觉得还差点意思，有更好的稿子可以补进去
- 作者风格随时间演化，想让指纹跟上变化

操作：
1. 在指纹面板里点某一条的 **打磨** 按钮（铅笔图标）。
2. `DistillDialog` 会以"打磨模式"打开，标题显示 **"打磨文风：XXX"**。
3. 加入新稿子 → 提炼 → 预览 → 保存。

打磨时代码做的事（用户看不见但要知道）：
- 指标按 **0.4 旧 : 0.6 新** 加权合并
- 旧范文和新范文合并后按前 50 字去重
- L0 规则按 when+do 指纹去重合并
- **即使 L0 提取这一步失败，旧规则也不会被擦除**

保存时会覆盖原指纹（`id` 不变，`sourceCount` 累加）。

### 5.4 导出 / 删除

- **导出为 Markdown**：展开指纹卡片，点导出按钮，会下载一份 `fingerprint-{名字}.md`，包含 L1/L2/L3 全部内容（由 `fingerprintToMarkdown` 生成）。适合备份或跨设备迁移。
- **删除**：点删除按钮，会二次确认。如果删的是当前 session 正在应用的，会自动清空 session 的 `fingerprintId` 字段。

### 5.5 常见问题

**Q: 提炼出来的画像有些字段是空的，是 bug 吗？**
A: 不是。`parseProfileFromLlm` 会严格丢弃类型不对/枚举非法/描述为空的字段。LLM 没把握的字段直接置 null 是鼓励的行为——宁缺勿滥。展开日志里的"风格画像解析完成"条目，`warnings` 会告诉你哪些字段被丢了、为什么。

**Q: 样本只有 1~2 篇，能不能也提炼？**
A: 能，但意象/主题层会被跳过（日志里会有 warn）。建议至少 3 篇再做。

**Q: 我改了指纹的 JSON 文件手动编辑，保存后生效吗？**
A: 指纹存在 `localStorage` 里，key 是 `studyRoom:fingerprint:{id}`，格式是完整的 `WriterFingerprint` JSON。手动编辑理论上可以，但**不推荐**——下次打磨时合并逻辑可能不符合预期。想改规则/画像建议走打磨流程。

**Q: 为什么激活指纹后写出来的东西有时候还是"AI 腔"？**
A: 检查几点：
1. 确认指纹真的应用到了当前 session（看顶部琥珀色提示）。
2. 看指纹有没有 `behaviorRules`（L0 规则是 v3 注入的主力）。没有的话效果会降到"只用范文 few-shot"级别。
3. 样本文本质量：范文如果本身就 AI 味很重，提炼出的指纹也会继承这种味道。
4. LLM 模型本身：某些小模型对"人格扮演"类提示词响应弱，换更强的模型会有显著改善。

**Q: 后端服务没起来能用吗？**
A: 部分能用。`listFingerprints` / `getFingerprint` / `saveFingerprint` / `deleteFingerprint` 都有 localStorage 降级，读写不受影响。但 `distillFingerprint` 第一步要调后端 `distill-prepare` 算 L1 指标，**这步必须有后端**（要求 `duncrew-server.py` 在端口 3001 跑着）。

## 六、关键设计决策

这一节集中解释几个"为什么这样做而不那样做"的取舍。

### 6.1 为什么提炼 → 预览 → 保存分成三段

最直接的理由：**让失败无成本**。

LLM 有时候会抽风：
- 幻觉出离谱的画像（把散文作者判成"反问密度 80%"）
- 网络波动中途报错
- 用户自己发现范文选错了

如果提炼完就直接落盘，用户只能通过删除来撤销，但旧指纹如果是打磨覆盖保存的就找不回来了。预览阶段的存在让用户有"看清楚再决定"的机会，也让 `distillFingerprint` 函数保持纯粹（只生成草稿，不碰存储）。

### 6.2 为什么多样本阈值硬编码为 3

代码注释：

> 经验值，不走配置，如需调整直接改此处。

选 3 的理由：
- **2 不够**：2 条样本出现同一个意象可能是作者在同一个时期的特定主题，不是风格特征
- **4+ 太高**：对新手用户门槛太高，很多人手头只有 3~5 篇代表作
- 3 是"能观察到重复模式"的最低可信门槛

意象/主题层被跳过时，系统不是偷偷跳过，而是在日志里明确 warn：

```
样本数 2 < 3, 意象/主题层将跳过
避免单篇样本凭感觉编 "高频意象 / 隐喻来源 / 引用偏好", 等样本累积到 3 篇再提取。
```

### 6.3 为什么 L0 规则用 when+do 做指纹

合并场景下要判断"旧规则 A 是否等同于新规则 B"。可选的策略：

| 策略 | 问题 |
|---|---|
| 用 LLM 给的 `id` | L0 提取器是无状态的，每次给的 id 不同，没用 |
| 全文对比 | `not` 和 `examples` 会随样本变化，全文 diff 会漏掉实质相同的规则 |
| **when+do 归一化指纹** | 只看"情境 + 动作"这个核心不变量 |

归一化处理（小写 + 空白折叠 + 去标点）解决了 LLM 同一意思换措辞的问题：

```ts
"当读者可能抵触时"  → "当读者可能抵触时"
"当读者可能抵触时。" → "当读者可能抵触时"  // 去句号
"当 读者 可能 抵触时"→ "当 读者 可能 抵触时"
```

**合并的决定性优先级**：新规则优先保留（按 LLM 返回顺序=区分度降序），旧规则按指纹补入兜底。这种设计对应了代码注释里的原则：

> LLM 已经通过 baseRules 参数做过"印证强化"的智能合并，这里再做一次确定性兜底——即使 LLM 忽略了某条旧规则，也不让它凭空消失。

### 6.4 为什么 v3 把 profile 从写作 prompt 里移除

这是最反直觉的决定。`formatFingerprintV2` 的注释：

> 架构原则：解耦"给人看的分析 (UI)" 和 "给模型用的提示 (prompt)"。profile/metrics 不再注入写作 prompt，只保留给 UI 展示。

理由有二：

1. **profile 对 LLM 是二手信息**。它本身就是 LLM 从原文归纳出的描述，再把描述喂回去是信息损耗——不如直接给 L0（具体规则）+ L3（原始范文），让 LLM 自己从源头吸收。
2. **避免 compliance-checking 模式**。列表化的"画像字段 = XX" 会触发 LLM 的合规核对心态，生成时边写边查 checklist，风格反而不自然。第二人称叙事式独白能让 LLM 进入"我就是这个人"的 style-absorption 模式。

代价：依赖 L0 规则的质量。所以 L0 提取器的 prompt 工程格外重要（多源印证 ≥ 2 条、when 要内部判断式而非位置等强约束都在 L0 prompt 里）。

### 6.5 为什么指纹不自动全局激活

`getActiveFingerprintId` 保留着，但 `resolveFingerprintForBrief` 只看 `brief.fingerprintId`：

```ts
// 设计权衡: 之前讨论时考虑过"active"全局激活模式, 但容易造成"用户以为 session 没指纹
// 结果其实默默应用了", 所以改为每个 session 显式指定.
```

"隐式全局状态"是最容易引起误解的 UX 反模式。用户在 session A 激活了"公众号腔"，忘了切出去就打开 session B 写严肃论文——LLM 默默按公众号腔写出来，用户可能看很久才意识到问题。显式 session 绑定虽然每次都要点一下，但错误可发现、状态可审视。

### 6.6 为什么存储分级（元信息索引 + 详情单独存）

```ts
const INDEX_KEY = 'studyRoom:fingerprints:index'     // WriterFingerprintMeta[]
const DETAIL_PREFIX = 'studyRoom:fingerprint:'       // 每个 id 一个 key
const ACTIVE_KEY = 'studyRoom:activeFingerprintId'   // string | null
```

注释里的理由：

> 为什么不统一存一个大数组：
> - 单个指纹可能上千字（含范文），频繁读写全部数据浪费
> - 列表页只需元信息，详情页才读完整数据（按需加载）

列表渲染只需要 `WriterFingerprintMeta`（几十字节/条）；展开详情时才 `readDetail(id)` 读单条。同时本地缓存 + 后端同步的双写策略让离线可用：

```ts
// saveFingerprint 的写入顺序
writeDetail(fp)   // 1. 本地先写（保证不丢）
writeIndex(metas) // 2. 索引更新
await fetch(...)  // 3. 后端尽力同步（失败静默）
```

## 七、未来演进

### 7.1 短期（已经有代码占位）

- **后端持久化完善**：当前 `saveFingerprint` 已经尝试 `PUT /api/study/fingerprints/{id}`，但后端侧还是 stub。等后端实现完，`localStorage` 自动降级为纯缓存。
- **提炼经验沉淀**：`distillLog` 已经落在指纹对象里了（`FingerprintPanel` 有 `DistillLogHistory` 展示历史）。未来可以把多次提炼的日志做成"演化史"视图，让用户看到指纹随时间的变化。

### 7.2 中期

- **多指纹混合**：当前 `brief.fingerprintId` 是单值。未来可以支持 `fingerprintIds: string[]` + 权重，让用户在"公众号腔 70% + 学术腔 30%"这种场景有明确表达。混合策略可以从行为规则层面做（规则池加权采样）或从范文层面做（不同指纹的范文混合 few-shot）。
- **细粒度规则编辑**：目前规则只能通过"打磨"间接修改。下一步考虑让用户在 `FingerprintPanel` 直接编辑某条 `behaviorRule` 的 when/do/not，甚至手动添加规则——本质是给高级用户一个绕过 LLM 提取的手动档。
- **指纹之间的可比较性**：提供两个指纹的"风格差异"视图（哪几维画像差得最远、哪些 L0 规则互相矛盾），方便用户理解自己积累的指纹库。

### 7.3 长期

- **指纹作为独立商品**：导出/导入 `.fingerprint.json` 文件，让作者之间可以分享指纹（"这是我提炼的 XX 作家风格指纹，送你"）。需要考虑版权和签名。
- **跨模态风格**：当前只处理文本。可以扩展到标题风格、排版风格（段落长度分布、分隔线习惯）、甚至 MD 格式偏好（加粗/斜体/引用的使用频率）。这些已经在 `metrics` 的 `[extra]` 扩展槽里预留了空间。
- **自学习打磨**：用户每次对 LLM 生成的文本做的编辑本身是"风格信号"——如果用户频繁把 A 改成 B，说明 A 不符合风格、B 才是。可以在自习室的编辑历史里提取这种 "A→B 修正对"，自动喂给 L0 提取器做持续打磨。
